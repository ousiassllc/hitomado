# Google Play での配布の準備（調査結果。#91）

> 関連: [Android ビルド](android.md) / [Android 版の試作と調査の結果](android-investigation.md) / [非機能要件 §2・§8](../requirements/non-functional.md) / [README の OAuth クライアントの作り方](../../README.md#oauth-クライアントの作り方)

Issue #91 は、Android 版を Google Play で配るために要る手続きと審査を、**調べて整理するところまで**の Issue である。**申込み・登録は一切していない**（必要になったときに改めて判断する）。本書は調査結果の一覧で、現時点の方針（**Android 版は GitHub Releases の検証用 APK として配る。Play には出さない**。[NF-D06](../requirements/non-functional.md)）は変えない。

- 調査日: 2026-11-06。一次情報は各節の末尾に URL を付けた。Google の文書は更新されるため、**着手するときに読み直す**。
- 文中の **[推測]** は、公式の文書に明記がなく、こちらの読み取りによる判断。**[未確認]** は、試していない・確かめられていないこと。
- アプリの現状（権限・通信先・保存するデータ）は、リポジトリの文書とコード（`AndroidManifest.xml`・[非機能要件 §2](../requirements/non-functional.md)・[機能要件 F-01](../requirements/functional.md)）から取った。

## 0. 結論

1. **Gmail の制限付きスコープ（`gmail.modify`）の Google による審査は、現行の BYO（利用者が自分の Cloud プロジェクトで OAuth クライアントを作る）のままなら、公開者（こちら）としては要らない** [推測]。Windows 版と同じ扱いで、Play に出しても変わらない。審査は「スコープを要求する Cloud プロジェクト」が受けるもので、BYO では各利用者のプロジェクトがそれに当たり、公式の「審査が要らない場合」の「個人利用」に当てはまるため（§4）。**公開者がクライアントを同梱して全員で共用する形に変えると、審査（ブランド確認＋制限付きスコープの審査）が要る**（§4.3）。
2. **Play 側の審査で最も重いのは、Gmail の審査ではなく「審査担当者がアプリにログインできるか」** である。Play は、ログインが要るアプリに、いつでも使える審査用のログイン情報を求める。Hitomado は**利用者が自分で OAuth クライアントを作らないと Gmail に繋がらない**ので、審査用の入口（テスト用のクライアントとアカウント、または審査用のデモ表示）を用意する必要がある（§5）。これは外部要因ではなく**こちらの実装・運用の判断**で、配布の可否を左右する。
3. **Play に出す前に直す必要があったビルドの問題が 1 つ見つかり、#205 で直した**: `libwails.so` の ELF セグメントの整列が 4KB（`Align 0x1000`）のままで、**16KB ページ対応の要件を満たしていなかった**。targetSdk 35 以上のアプリは 64 ビット端末で 16KB ページに対応する必要があり、**2027-02-01 以降は対応していない更新を Play にリリースできない**（§6.1。現在は 16KB 整列で、`android:verify` が検査する）。
4. 個人アカウントの場合、**12 人のテスターを 14 日間連続でクローズドテストに参加させてからでないと本番公開できない**（§2.2）。組織アカウントなら D-U-N-S 番号が要り、取得に最大 30 日かかる。どちらにするかは未決（§8）。
5. 費用は **Play Console の登録料 US$25（一度だけ）**。Google の審査（OAuth）には費用の記載がない。審査を受ける場合の外部評価（CASA）は有料のことがあるが、サーバーを持たない現行の構成では対象外の見込み（§4.3 [推測]）。

## 2. Play Console のアカウントと配布の流れ

### 2.1 アカウント

- **登録料は US$25（一度だけ）**。クレジットまたはデビットカード（プリペイドは不可）。**18 歳以上**。登録の過程で、法的氏名で政府発行の ID とクレジットカードを求められることがあり、無効と判断されると登録料は返金されない。
- **アカウントの種類**は個人と組織の 2 つ。金融・健康・VPN・政府系のアプリは組織が必須だが、Hitomado はどれにも当たらないので**どちらでも登録できる**。
  - 個人: 法的氏名・住所・連絡先メール・電話・開発者メール。Google の決済プロファイルの氏名・住所が使われる。**Google Play に、法的氏名・国・開発者メールが公開される**（収益化すると住所も公開）。連絡先メール・電話・開発者メールはワンタイムコードで確認し、アカウントが続く間は使える状態を保つ。
  - 組織: **D-U-N-S 番号（無料。Dun & Bradstreet が発行。新規取得に最大 30 日）**・組織名・住所・電話・Web サイト・連絡担当者。D-U-N-S の情報と Play の登録情報は一致させる。**組織の法的氏名・住所・開発者メール・電話が Google Play に公開される**。
- 個人アカウントは、**公開の前に Play Console のモバイルアプリで Android 端末の確認**が要る。
- 情報は後から追加・更新できるが、登録時に選んだ**アカウントの種類**による条件（§2.2 のテスト要件など）は、登録の日付（2023-11-13 より後か）で決まる。
- 出典: [Get started with Play Console](https://support.google.com/googleplay/android-developer/answer/6112435)・[Required information to create a Play Console developer account](https://support.google.com/googleplay/android-developer/answer/13628312)・[Play Console Requirements](https://support.google.com/googleplay/android-developer/answer/10788890)（いずれも 2026-11-06 に確認）。

### 2.2 テストのトラックと本番公開

| トラック | 要件 | 備考 |
|----------|------|------|
| 内部テスト | なし（アプリの設定の前でも使える） | 内部テストだけなら、データセーフティの入力は不要。配布先は少数の信頼できるテスター |
| クローズドテスト | アプリの設定（App content など）の完了 | **個人アカウント（2023-11-13 以降に作成）は、本番公開の申請時に 12 人以上のテスターが、直前の 14 日間連続で参加していること**。申請ではテストの内容や準備状況の質問に答える |
| オープンテスト | 本番公開へのアクセスを得ていること | |
| 本番 | 個人アカウントは上のクローズドテストの要件を満たし、申請が通ること。組織アカウントには、この文書の範囲でテスト要件の記載はない | |

- 実際に公開するときの現実的な最短は、**アカウントの確認 → App content と掲載情報の完了 → クローズドテスト 14 日 → 本番公開の申請 → Play の審査**（個人アカウントの場合）。テスターの 12 人は Google アカウントを持つ人で、連続 14 日の参加を保つ必要がある。人集めはこちらの作業になる（**規模が読めない要素**）。
- 出典: [App testing requirements for new personal developer accounts](https://support.google.com/googleplay/android-developer/answer/14151465)。

### 2.3 アプリの作成と署名

- アプリを作るとパッケージ名が Play に自動で登録され、アカウントに紐づく。他の開発者が使っている名前だと別の名前を求められる（`jp.ousias.hitomado` は、一次情報で未使用かは確認できていない [未確認]。作成時にわかる）。出典: [Android developer verification（Play Console）](https://developer.android.com/developer-verification/guides/google-play-console)。
- **AAB で公開する**。署名は Play App Signing（Google が配布用の鍵を保管し、**こちらが持つのはアップロード鍵**。[Android ビルド §4](android.md#4-署名)）。アップロード鍵を失うとアップロードの再設定が必要になる（鍵の保管は §6.2）。
- 版番号は既存のとおり（[Android ビルド §5](android.md#5-版番号)）。**同じ `versionCode` は二度上げられない**。

### 2.4 ストア掲載情報

- アイコン: 32 ビット PNG（アルファ付き）、512×512、1024KB 以下。フィーチャーグラフィック: JPEG か 24 ビット PNG（アルファなし）、1024×500。スクリーンショット・短い説明・長い説明。出典: [Add preview assets](https://support.google.com/googleplay/android-developer/answer/9866151)。
- アセットは Google が宣伝にも使える（開発者配布契約）。
- Hitomado の UI は日本語のみ（[NF §7](../requirements/non-functional.md)）。掲載情報の言語（日本語のみで始めるか、英語を併記するか）は未決（§8）。**審査用のログイン情報は英語で書く必要がある**（§5）。

## 3. データセーフティの記入内容

**入力が要るのは内部テスト以外のトラックを使うとき**（内部テストだけのアプリは不要）。「何も収集しないアプリ」でも、フォームの入力とプライバシーポリシーの URL は必須。入力内容はアプリの実際の動きと**プライバシーポリシーの記述に一致**させる（食い違いは執行の対象）。

### 3.1 プライバシーポリシー

- **ストアの掲載ページとアプリ内の両方**にリンクが要る。現状、**アプリ内にプライバシーポリシーへのリンクは無い**（`frontend/src` に該当の記述なし）。**公開の URL も無い**。
- 条件: 有効な SSL の公開 URL（`https://`）、ログインや地域の制限なし、通常の Web ページ（PDF やダウンロードは不可）、**このアプリに固有**で、データの収集・使用・共有（共有先の種類を含む）を網羅して書く。
- 載せる内容（現状の動きから）: 公開者のサーバーは持たず、テレメトリ・クラッシュレポートの自動送信は無い（[NF §2](../requirements/non-functional.md)）／メールの内容は Google の API から端末へ取得し、DB に保存するのはメタデータ・スニペットだけで本文は保存しない（[README](../../README.md)）／資格情報は端末の Keystore で暗号化／AI 下書きではスレッドの一部が、利用者が選んだ AI プロバイダへ、同意のうえ送られる／アカウント削除とアンインストールでデータが消える／**Google API のデータの扱いが「Limited Use」の要件に従う旨**（Gmail のスコープで得たデータは、アプリの画面に出ている機能のためにだけ使い、広告・売買・機械学習の学習に使わない）。
- 出典: [Prepare your app for review](https://support.google.com/googleplay/android-developer/answer/9859455)（プライバシーポリシーの要件）、[Google Workspace user data and developer policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)（Limited Use の表記例）。

### 3.2 記入案

Play の定義では、**「収集」＝アプリが利用者のデータを端末の外へ送信すること**（SDK・ライブラリ経由を含む）。端末の中だけで処理して外へ出さないデータは申告不要。**「共有」＝収集したデータを第三者へ渡すこと**で、サービス提供者（開発者の指示で処理する者）への委託、法的目的、**利用者が自分で起こした操作で、利用者がその共有を当然と考えるもの**、または目立つアプリ内の説明と同意に基づく転送は、共有の申告から除かれる。

| 項目 | 記入案 | 根拠（アプリの動き） |
|------|--------|----------------------|
| 公開者へ送るデータ | **なし**（公開者のサーバーを持たない。テレメトリ・クラッシュレポートの自動送信なし） | NF §2 |
| 収集: メッセージ → **メール** | 収集する（目的: アプリの機能。必須）。端末から Gmail の API へ、返信・転送・下書き・送信・ラベル変更の内容を送る | F-04〜F-06・F-11・F-12 |
| 収集: 個人情報 → **メールアドレス**・**名前** | 収集する（目的: アプリの機能、アカウント管理）。OAuth の `openid email profile` で取得し、Google へのリクエストと端末の DB で使う | F-01 |
| 収集: ファイルとドキュメント | 添付の送信（F-14）で、利用者が選んだファイルを Gmail へ送る。**収集として申告する**案 | F-14 |
| 収集: 位置情報・連絡先（連絡先 API）・デバイス ID・広告 ID・購入履歴・健康・財務・写真と動画・音声・カレンダー・アプリのアクティビティ・Web 閲覧履歴 | **なし**。宛先候補は受信メールのヘッダから作るもので、連絡先 API は使わない | manifest の権限（`INTERNET`・`ACCESS_NETWORK_STATE`・`VIBRATE`・`POST_NOTIFICATIONS` ほか WorkManager の 2 つ） |
| 収集: アプリの情報とパフォーマンス（クラッシュログ・診断） | **なし**。ログは端末内のファイルだけで、自動では送らない（利用者が「ログを書き出す」で保存する） | NF-S10・[Android ビルド §13](android.md) |
| 共有 | **しない**案。Gmail への送受信は Google 自身（利用者のメールの提供元）への操作で、利用者が起こした操作。**AI 下書き**（利用者が選んだ提供元へスレッドの一部・表示名・署名を送る）は、初回に「内容が選択した提供元へ送信される」ことを表示して同意を取り、同意前は送らない（[NF §2](../requirements/non-functional.md)）ので、「目立つ説明と同意に基づく転送」として共有の申告から除く判断 [推測] | NF §2・F-08 |
| 任意か必須か | メール・アドレス・名前は**必須**（これらが無いとアプリが使えない）。AI 向けの送信は**任意**（機能ごとオフにできる。設定しないかぎり送らない） | F-08 |
| 転送中の暗号化 | **する**（Google・AI プロバイダとの通信はすべて HTTPS。`http://` は `localhost` 等のローカルの AI サーバーだけ許可。NF §2） | NF §2 |
| データの削除 | アプリ内にアカウントの削除がある（トークン・キャッシュ・署名・色を削除し、可能なら Google 側のトークンも revoke）。端末内のデータはアンインストールで消える（クラウドバックアップも無効。`allowBackup=false`）。公開者側にデータは無い | F-01・manifest |
| 独立したセキュリティの審査 | 受けていない | — |
| ファミリー向けのアプリ | **対象外**（13 歳未満向けでない） | §3.3 |

注意:

- 「メール」を**収集**と申告するか（端末から利用者自身の Gmail へ送るだけで、公開者は受け取らない）は、Play の定義（端末の外への送信＝収集）に従うと申告する側に倒れる。ここは**申告漏れのリスクのほうが重い**ので、収集として記入する案にした。最終の記入は Play Console の画面の選択肢（データの種類・目的）を見て決める [推測]。
- **AI プロバイダの扱い**はデータセーフティだけでなく、Google の Gmail の規約（Limited Use。§4.2）でも問題になる。プライバシーポリシーと一致した記述にする。
- ライブラリ（Wails・androidx security-crypto・WorkManager など）が端末の外へデータを送らないことを、**着手時に再確認する**（WebView は Wails のローカルのアセットを表示するだけだが、メール本文の「画像を表示」は利用者の操作で外部の画像を取得する）。
- 出典: [Provide information for Google Play's Data safety section](https://support.google.com/googleplay/android-developer/answer/10787469)。

### 3.3 そのほかの App content の宣言

| 宣言 | 回答案 | 備考 |
|------|--------|------|
| 広告 | **広告なし** | 広告 SDK を入れていない |
| 対象年齢・内容 | **13 歳未満向けではない**（一般向け） | Google API のデータを使うアプリが子ども向けだと、Google のポリシー（[API Services User Data Policy](https://developers.google.com/terms/api-services-user-data-policy)）に反する |
| 機密性の高い権限（SMS・通話履歴・位置情報など） | **なし** | manifest にない（`CAMERA`・位置情報・生体認証は削除済み。[Android ビルド §6](android.md#6-manifest-と検査)） |
| 前面サービスの宣言 | **要らない** | `FOREGROUND_SERVICE` 系の権限と前面サービスを #88 で削除済み（バックグラウンド同期は WorkManager。[Android ビルド §15.7](android.md#157-manifest-の整理)） |
| ログイン情報（Sign-in details） | **要る**（§5） | |
| アカウントの削除 | アプリ内の「アカウントの削除」と、削除の要求ができる Web ページの用意が要るか、**着手時に確認** | Play の要件は「アプリ内でアカウントを作れる場合」に、アプリ内と Web の両方で削除の入口を求める。Hitomado に**アプリ独自のアカウントは無い**（Gmail の接続だけ）ので、対象外と答える見込み [推測]。ただし Play Console の質問の文面で再確認する。データ削除の説明は §3.2 のとおり |
| レーティング（IARC の質問票） | 暴力・性的内容・ギャンブルなどを持たない内容で回答 | 回答するとレーティングが付く |

出典: [Prepare your app for review](https://support.google.com/googleplay/android-developer/answer/9859455)・[App account deletion requirements](https://support.google.com/googleplay/android-developer/answer/13327111)。

## 4. Gmail の制限付きスコープの審査

### 4.1 前提

- `gmail.modify` は **制限付き（Restricted）スコープ**（[Gmail API のスコープ](https://developers.google.com/workspace/gmail/api/auth/scopes)）。ほかに `gmail.readonly`・`gmail.compose`・`mail.google.com` なども制限付き。非機密で使えるのは `gmail.labels` ほか add-on 用のものだけで、**メール本文の読み取り・返信の送信を `gmail.modify` より狭いスコープで代える方法は、Hitomado の機能（読む・ラベル・下書き・送信・ゴミ箱）では無い**（`gmail.readonly` も制限付き）。スコープは現行のままにする（NF-S02）。
- 制限付きスコープを要求する**公開されたアプリ**は、Google の審査（OAuth アプリの審査）を受ける。審査は、**スコープを要求する Cloud プロジェクト（OAuth クライアントを持つ側）の「同意画面のブランド」について**行い、公開後は年 1 回の再確認がある。審査の内容: ブランドの確認（アプリ名・ロゴ・ホームページ・プライバシーポリシー。ホームページとポリシーは**同じドメイン**で、Search Console でドメインの所有を確認する）、スコープごとの利用目的の説明、**許可された用途**であること、Limited Use の遵守。**サーバーでデータを保存・送信する、またはサーバー経由でアクセスできるアプリは、さらに外部の評価機関によるセキュリティ評価（CASA。毎年）が要る**。
- Gmail で許可されている用途（[Google Workspace user data and developer policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)）: **メールクライアント（読む・書く・送る・処理する画面を持つもの）**、バックアップ、生産性を高めるアプリ（生成 AI による要約を含む）、メールの情報を使うレポート・監視。Hitomado は 1 番目（メールクライアント）に当たる。許可されない用途（モバイルキーボード、手動の一回きりのエクスポート、複数アカウントによるポリシー回避など）には当たらない。

### 4.2 Limited Use と、Hitomado の現状

Gmail のスコープで得たデータは、次のとおりに扱う必要がある（[API Services User Data Policy](https://developers.google.com/terms/api-services-user-data-policy)）。審査を受けない BYO の場合も、**Google API を使うアプリとしてこのポリシーに従う前提**で作るのが安全である [推測]。

| 要件 | Hitomado の現状 |
|------|----------------|
| データの使用は、アプリの画面に出ている機能のためだけ | 満たす（受信箱・返信・AI 下書きなど。広告・解析に使わない） |
| 第三者への転送は、機能の提供のために**利用者の同意**があるときだけ | AI 下書きで、初回の同意のあとに限り、スレッドの一部を利用者が選んだ AI プロバイダへ送る（NF §2）。同意の画面の文言は「スレッドの本文の一部・差出人・日時と、あなたの表示名・署名が <提供元>（<URL>）へ送信されます。AI への指示を入力した場合は、その指示も送信されます。新規作成の下書きでは、スレッドの代わりに、AI への指示と、入力済みの件名・宛先（To）が送信されます」（`frontend/src/lib/messages/compose.ts` の `consentBody`）で、メールの内容が送られることは読み取れる（Gmail のデータとまでは書いていない） |
| 人が読んではならない（利用者の同意・セキュリティ・法令・匿名の集計を除く） | 公開者のサーバーが無く、公開者はデータを見られない |
| データを機械学習の学習に使わない（利用者本人向けの機能を除く） | 公開者は使わない。**AI プロバイダ側で学習に使われないかは、プロバイダの規約と利用者の選択に依存する**ので、ポリシーに書く [推測] |
| 認証情報・トークンは暗号化して保存 | 満たす（Android Keystore の鍵で暗号化。NF-S01） |
| 通信は HTTPS | 満たす |
| プライバシーポリシーに、Limited Use に従う旨の記述 | 未作成（§3.1） |
| **アプリ内の目立つ説明（Prominent Disclosure）**: データの種類・使い方・共有を、同意の直前に、設定画面ではなく通常の使用の流れの中で表示する | **現状は無い**。アカウント追加の画面に説明を足す必要がある（配布の前の実装作業） |

### 4.3 Android 版で審査が要るか

| 構成 | 審査 | 理由 |
|------|------|------|
| **BYO のまま**（現行）。利用者が自分の Cloud プロジェクトで「デスクトップ アプリ」のクライアントを作り、Client ID／Secret を設定に登録する | **公開者としては不要** [推測] | 審査を受けるのは「スコープを要求する Cloud プロジェクトの持ち主」。BYO ではそれが各利用者で、利用者は自分のクライアントを自分のアカウントでだけ使う。Google の文書の「審査が要らない場合」に **「個人利用（自分だけ、またはごく少数の知り合いだけが使う）」** と **「開発・テスト」**・**「Workspace の組織内だけの利用（同意画面を内部にする）」** がある。**未確認のアプリの警告画面**は出る（利用者が「詳細→移動」で進む。README に手順がある）。**未確認アプリの利用者数の上限（100 人）**は、各利用者が自分のプロジェクトで 1 人（または数人）しか使わないので問題にならない |
| **公開者が OAuth クライアントを 1 つ持ち、アプリに同梱して全員で共用する** | **必須**（ブランド確認＋制限付きスコープの審査。数週間かかる文書の記載） | 「公開されたアプリ」になる。CASA（外部の評価）は、**サーバーを通ってデータにアクセスする場合**が対象で、Hitomado はサーバーを持たない（端末から Google へ直接）ので**対象外の見込み**。ただし **AI 下書きで端末から第三者の AI プロバイダへデータを送る点が、評価で論点になる可能性がある** [推測]。Android 版でも Windows 版でも条件は同じ |
| Android クライアント種別（パッケージ名＋署名鍵）＋カスタムスキーム | 採らない | Google が Android でのカスタム URI スキームを使えなくしている（[Android ビルド §14.1](android.md#141-決定)）。審査の要否とは別の理由 |

- **Play に出すこと自体は、Google の OAuth の審査の要否を変えない**。Play の審査（ポリシー適合）と Google OAuth の審査は別の仕組みで、前者は後者の通過を要件にしない [推測。Play の文書に OAuth の審査を求める記述は見つからなかった]。
- **BYO のままでの問題は、審査ではなく使いやすさ**。Play で一般の利用者に配ると、利用者の全員が、Cloud プロジェクトの作成・Gmail API の有効化・同意画面・クライアントの作成を自分で行う必要がある（README の手順で 6 ステップ）。外部かつ「テスト」のままだとリフレッシュトークンが 7 日で失効する。**一般向けの配布としては利用者の負担が非常に大きい**ので、「共用クライアント＋審査」の選択肢を含めて、出すと決めるときに判断する（§8）。
- 組織の Workspace の「内部」アプリなら審査は要らないが、組織のアカウントだけで使える。
- 出典: [Restricted scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)（審査が要らない場合・CASA）、[Unverified apps](https://support.google.com/cloud/answer/7454865)（100 人の上限・警告画面）。

## 5. Play の審査で「ログインできるか」

- Play は、アプリの一部または全部がログインで制限されているとき、**審査担当者が全機能にアクセスできる情報**（ログイン情報・手順）を **App content の Sign-in details** で求める（Play Console Requirements の「デモアカウントとログイン情報」）。条件: **いつでも・何度でも・地域に関係なく使える**、誤りなく保たれる、2 段階認証やワンタイムパスワードを避けられる、**英語で書く**、ほかのアカウント（Google でのログイン等）が絡むときは手順を詳しく書く。パスワードの期限切れなどで入れないと、審査が通らず**リジェクト**される。
- Hitomado の場合、審査担当者が使えるようにするには、次のどれかが要る:

  | 案 | 内容 | 利点・難点 |
  |----|------|------------|
  | A. テスト用の Cloud プロジェクト＋Gmail アカウントを用意し、Client ID/Secret とアカウントの情報を Sign-in details に載せる | 公開者が審査用のクライアントとテスト用の Gmail を持つ | 実装は要らない。難点: Google 側で、そのアカウントの 2 段階認証やログインの確認（新しい端末からのログイン）が出て、**「いつでも使える」を保てない恐れ**。同意画面が「テスト」だと 7 日でトークンが切れるので「本番」にして未確認のまま使う（警告画面が出る）。**アカウントの資格情報を Play に渡す**ことになる [推測] |
  | B. 審査用のデモ表示（シード済みのフェイクの Gmail。`internal/e2e` のものを流用できる） | 本番のビルドに、審査用の入口（例: 設定の隠し操作・専用のビルドバリアント）を持たせる | ログインの問題が消える。難点: **実装が要る**。本番ビルドに入れると、審査のための迂回が製品に残る。Play の「正確な機能の説明」に反しない形（デモであることを明記）にする必要がある |
  | C. 共用クライアントを持つ（§4.3） | 審査用のログインは、その 1 つのクライアントとテスト用の Gmail | 利用者の負担も減る。難点: Google の審査が必須。Gmail のテスト用アカウントの問題は A と同じ |

- **推奨は未決**。A は実装が要らないが、Google の側の都合で崩れやすい。B は確実だが実装が要る。着手するときに、悠太さんが選ぶ（§8）。
- 出典: [Requirements for providing sign in details for review](https://support.google.com/googleplay/android-developer/answer/15748846)・[Play Console Requirements §3.3](https://support.google.com/googleplay/android-developer/answer/10788890)。

## 6. ビルド・署名の前提

### 6.1 16KB ページ対応（対応済み。#205）

- **要件**: targetSdk 35 以上のアプリは、Google Play で **64 ビット端末の 16KB メモリページに対応する必要がある。2027-02-01 以降、対応していない更新はリリースできない**。Play Console に警告が出る。出典: [Support 16 KB page sizes](https://developer.android.com/guide/practices/page-sizes)。
- **対応前の状態**: #81 の試作ブランチ（`proto/android-81`）のビルド成果物（NDK 26.3.11579264）の `libwails.so` を `readelf -lW` で見ると、**arm64-v8a・x86_64 とも、すべての `LOAD` セグメントの `Align` が `0x1000`（4KB）**だった。16KB に対応するには `0x4000` 以上が要る。
- **対応（#205）**: `build/android/Taskfile.yml` の `compile:go:shared` の `BUILD_FLAGS` に、リンクの引数 `-extldflags=-Wl,-z,max-page-size=16384` を足した（release は `-ldflags="-w -s -X … -extldflags=…"`、debug は `-ldflags="-extldflags=…"`）。NDK は 26.3.11579264 のまま。Go の c-shared のリンクはこの指定を受け付け、ビルドした release の APK・AAB の `libwails.so`（arm64-v8a・x86_64）と debug の x86_64 ビルドで、すべての `LOAD` セグメントの `Align` が `0x4000` になった（`readelf -lW`）。
- **検査**: `build/android/scripts/check-elf-align.sh` が `readelf -lW` で、すべての `LOAD` セグメントが `0x4000` 以上であることを確かめる（PATH の `readelf`／`llvm-readelf`、無ければ NDK の `llvm-readelf`）。`verify-apk.sh`（`task android:verify`。CI の APK の検査も同じ）が APK 内の `lib/*/libwails.so` ごとにこれを呼ぶ。検査そのものの回帰テストは `check-elf-align_test.sh`（ホストの `cc` で 4KB・16KB 整列の `.so` を作って確かめる。CI の `ci.yml` が実行）。
- **Play に出さなくても影響がある**: 16KB ページの端末（Android 15 以降で設定できる端末）では、4KB 整列の `.so` は読み込めない恐れがある [推測]。GitHub Releases の APK でも、そういう端末では起動しない可能性があった。出す・出さないの判断とは独立に直した。APK 内の `.so` を圧縮して格納している（[Android ビルド §6.1](android.md#61-so-と-dex-を圧縮して格納するサイズ優先)）点は、16KB 対応の可否とは別（zipalign の整列の対象は無圧縮の場合）。
- **未確認**: 16KB ページのエミュレーター（16KB のシステムイメージ）での起動。

### 6.2 署名鍵

- 現在の Release の APK は、GitHub Secrets の**固定鍵**で署名している（版が変わっても署名が同じで、上書きインストールで更新できる。作り方・Secrets の登録・控えは [Android ビルド §4.1](android.md#41-リリースの固定鍵github-secrets310)。#310）。Play に出すには、**恒久のアップロード鍵**を作り、リポジトリの外（パスワードマネージャー等）と GitHub Secrets に置いて、CI（`release.yml`）で署名した AAB を作る必要がある。署名の仕組み（環境変数 4 つ）は実装済み（[Android ビルド §4](android.md#4-署名)）。
- **Play に出した後は、GitHub Releases の APK と Play 版で署名が違う**（Play App Signing では Google の鍵で再署名される）。同じ端末で入れ替えると署名が合わず、いったんアンインストールが要る。Releases の APK を続けるか、Play に一本化するかは未決（§8）。

## 7. 関連: Android の開発者確認

Google は 2026 年から **Android の開発者確認**（アプリのパッケージ名の登録と開発者の本人確認）を段階的に始める。**2026-09-30**に、ブラジル・インドネシア・シンガポール・タイで、対象のストアからアプリを入れる認定端末で保護が始まり、**2027 年以降に世界へ広げる**予定。Play に出すアプリは、**Play Console が自動でパッケージ名を登録する**（99% のアプリ）。Play の外（今の GitHub Releases の APK）で配り続ける場合は、別の登録（Android Developer Console。限定配布のアカウントは 20 台までの配布で、政府発行の ID も登録料も不要）が必要になる可能性がある。出典: [Android developer verification](https://developer.android.com/developer-verification)（2026-11-06 に確認）。

- 日本でいつから対象になるか、GitHub の APK を直接入れる利用者にどう影響するかは、**この調査では確認できていない** [未確認]。Play に出す・出さないの判断とは別に、検証用 APK の配布を続けるなら、2027 年に向けて**確認が要る**。

| 文書の改訂 | README・NF-D05／NF-D06・F-16・[Android ビルド §8・§10](android.md)・[Android 版の試作と調査の結果](android-investigation.md) の「Play では配布しない」の記述を、出すと決めたときの方針に改める | S | なし |
| 共用クライアントを選ぶ場合 | ブランド確認（ホームページ・ポリシー・Search Console）＋制限付きスコープの審査。CASA が要るかの確認 | L | **数週間**（Google の文書の記載） |

**総じて**: こちらの作業（実装・文書）は合計で M〜L。実時間を決めるのは、(1) 個人アカウントなら 12 人×14 日、組織なら D-U-N-S の最大 30 日、(2) 共用クライアントを選ぶなら Google の審査（数週間）、(3) 実機での確認、の 3 つ。規模は Issue の「規模: 未見積」の欄に対応する。
